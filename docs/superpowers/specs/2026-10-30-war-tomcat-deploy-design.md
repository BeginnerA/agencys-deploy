## 1. 目标、决策与演进顺序

### 1.1 已确认的产品边界

新增 `deploy_mode=war_tomcat`，在 Linux + systemd 目标机托管传统 WAR 应用。每应用独立 Tomcat 进程、HTTP 端口、`CATALINA_BASE` 和 systemd 单元；允许共用管理员预装的 `CATALINA_HOME`。

选择“固定实例，WAR 版本化”：实例配置不随应用版本切换，WAR 保存于版本目录。应用回滚只恢复 WAR，不自动恢复 Tomcat 配置、JDK、环境文件或数据库。单实例切换有停机窗口，不承诺零停机，也不自动转换 Java EE/Jakarta EE 应用。

首版包括 Maven 构建或外部制品投入、接入预览与确认、发布、显式回滚、失败恢复、重启、日志和每主机观测。发布及恢复成功都必须通过应用级 HTTP 健康检查，不能用 Java 进程存在或 systemd active 替代。

不包括共享 Tomcat 中多 WAR 托管、Manager 热部署、运行时在线安装/升级、自动建账号/改 sudo/开放防火墙、接管无平台归属的实例、数据库回滚和业务文件迁移。

### 1.2 三条线的顺序

| 子项目 | 与现有平台的关系 | 当前阶段与进入下一阶段的条件 |
| --- | --- | --- |
| WAR/Tomcat | 新增 Linux 进程族模式，复用任务、SSH 和观测基础设施 | 本规格；用户审阅后编写实施计划，完成自动化及实际兼容验收 |
| Windows 服务 | 需要独立的目标机执行、路径、服务管理与凭据边界 | 未设计/未实现；WAR 阶段收口后单独 spec → plan → implementation |
| Kubernetes/Helm | 独立集群编排后端，面向集群/namespace/release，不套逐主机 systemctl 流程 | 未设计/未实现；单独设计资源、权限、凭据与回滚模型 |

Windows 便携包仅说明平台可以运行在 Windows 上，不代表支持 Windows 目标机服务部署。后两项不因本规格完成而被计入已支持能力。

### 1.3 方案取舍

采用独立 Tomcat 实例而非共享实例，减少停止、清缓存、回滚时对其他业务的影响；代价是更多 JVM 内存和端口。采用固定实例配置而非每版复制整个 Tomcat，避免把运行时升级与应用发布捆绑；代价是历史 WAR 必须仍兼容当前实例配置。

策略实现采用“复用安全的通用能力，WAR 自有严格生命周期”，不直接继承现有进程策略的全部切换/回滚行为，也不对旧七种方式做批量语义重构。

## 2. 现状差距与兼容原则

当前注册的七种模式是 `container`、`static_archive`、`jar_service`、`go_binary`、`rust_binary`、`node_process`、`python_process`。WAR 不得改变其产物选择、健康检查、版本号或既有配置默认值。

| 当前实现证据 | 与 WAR 契约的差距 | 本期最小扩展 |
| --- | --- | --- |
| `process_service.py` 的 file 上传及 archive 替换 | 已有版本可能被覆盖 | WAR 专用临时上传、校验和不可变提交 |
| `ProcessServiceStrategy.switch/rollback` | stop 允许失败；rollback 不含完整恢复后健康确认 | WAR 独立 stop → 确认退出 → 切换 → 启动 → HTTP 验证 |
| `Deployer.deploy_server` | rollback 抛异常后仍可能汇总为“已回滚”；首次失败保持新实例 | WAR 返回明确恢复结果；首次失败停止实例；未知状态不宣称成功 |
| `Deployer.run` 的自动回滚版本查询 | 使用首台读出的版本作为全局基线 | WAR 自动恢复使用加锁后逐主机快照；版本推荐与恢复基线分离 |
| 首台灰度回滚、`rollback_all` | 存在绕过统一恢复入口的路径 | 所有 WAR 入口进入同一严格主机操作服务 |
| `task_manager.py` 重启 | systemctl active 即通过初检，HTTP 超时仍可成功 | WAR 使用本模式 readiness，超时失败，覆盖远端互斥 |
| `monitor.py` 进程聚合 | 进程 online 不能证明 WAR 可服务 | 进程状态、应用健康、实际版本分开展示 |
| `_select_jar` | 候选多个时取最大，不适用 WAR | 独立 WAR 唯一候选选择器，旧 JAR 规则不动 |
| `service_unit.py`、unit 路由 | 只有 ExecStart 特征检查，无实例归属/指纹/确认摘要 | WAR 专用实例清单、预览摘要、漂移与锁校验 |
| `package_portable.py` 白名单 | 根目录 `service_unit.py` 未列入 SOURCE_FILES | 包内接入路径的依赖闭包必须通过导入和启动测试 |

新增能力开关默认关闭，只有 WAR 使用严格主机操作接口。不能只把 WAR 加入 `process_modes()` 就认为生命周期、重启与观测已适配。

## 3. 服务配置与统一校验

### 3.1 配置契约

继续使用服务的 `runtime_config`，不新建另一套服务配置数据库。`build_type` 使用现有 `maven`/`none`，版本沿用 semver。

| 字段 | WAR 首版规则 |
| --- | --- |
| `app_home` | 必填 Linux 绝对路径；实例、制品、状态根目录；接入后不可原地换根 |
| `tomcat_home` | 必填；已安装 Tomcat 根目录，即 CATALINA_HOME；允许多个实例共享但平台不写该目录 |
| `java_home` | 必填；已安装 JDK/JRE 根目录，使用其中 `bin/java` |
| `run_user` | 必填；目标机已存在、UID 非 0；必须与具备配置写权限的部署身份隔离 |
| `unit_name` | 可选；沿用统一派生规则；保存/比较时规范为同一个 `.service` 单元名，禁止模板实例和路径字符 |
| `port` | 必填整数，1024–65535；首版业务 Connector 监听 IPv4 `0.0.0.0`，隧道探活访问回环地址 |
| `context_path` | 必填；根应用可填 `/`，规范化为空；其他为 `/orders` 或 `/team/orders`，不允许末尾 `/` |
| `artifact_pattern` | 默认 `target/*.war`；相对每个构建搜索根；禁止绝对路径和 `..`；全候选只能有一个 |
| `jvm_opts` | 字符串数组；逐项编码到 systemd argv，不执行 shell；空数组为默认 |
| `env_files` | 绝对路径数组；引用目标机已有文件，不读取值、不传入预览、不复制到制品 |
| `stop_timeout` / `start_timeout` | 正整数，默认 60 / 120 秒；systemd 超时与平台等待边界一致 |
| `readiness.type` | 固定为 `http`；WAR 禁用 `process`/`tcp` 成功兜底 |
| `readiness.path` | 必填；相对应用根的绝对路径，如 `/health`，不是整个 URL |
| `readiness.expected_status` | 默认且首版仅支持 200 |
| `readiness.body_contains` | 可选非空固定文本；对响应正文做字面量包含检查，不猜测 `UP`/`ok` |
| `readiness.timeout` / `interval` | 默认 120 / 5 秒，正数；总等待与单请求超时共同受截止时间约束 |

`CATALINA_BASE={app_home}/instance`、工作目录、日志目录、docBase、启动主类都由平台派生，不接受任意 shell、`app_args`、`work_dir`、任意 XML 或自定义部署脚本覆盖。字段不适用时显式报错，而不是静默落入 Python 等分派末尾。

### 3.2 安全与冲突校验

Web 保存、YAML 导入、CLI、构建、接入和任务执行调用同一 WAR 规范化/校验器；执行前仍从最新记录重验，不能只信前端校验。

- 路径禁止根目录、空路径、控制字符、`..`、shell/systemd 插值字符和不受支持的编码；首版限制为普通 Linux 路径字符。所有远端使用处仍做参数编码与 XML 转义。`app_home` 与运行时目录不得相同或互相包含。
- `context_path` 的每段仅允许字母、数字、下划线、连字符；禁止 `.`、`..`、`#`、`%`、查询串、片段、重复斜线和编码分隔符。空 context 对应 `ROOT.xml`；多层 context `/team/orders` 对应 `team#orders.xml`。
- 健康路径只允许路径，不允许 scheme/host、查询、片段、控制字符、反斜线、编码穿越、重复斜线或 `..` 段。最终路径为 `context_path + readiness.path`；`/orders` 加 `/health` 得 `/orders/health`。
- `jvm_opts` 禁止换行、NUL、systemd 变量/说明符插值，并禁止覆盖 classpath、main class、`catalina.home/base`、临时目录和平台日志配置；不通过拼接 shell 实现转义。
- 版本号、制品名、unit 都独立做白名单校验。远端清理不得用未经校验的用户路径或通配符。
- 主机侧注册表检查根目录相同/嵌套、unit 重用和端口重用；接入还检查已有进程监听与目标单元，拒绝占用。不同 SSH IP/端口指向同一主机时，仍使用该主机唯一注册表。
- 非平台管理程序无法被平台锁约束；其后续占用端口或改文件应导致启动/漂移检查失败，不能声称彻底排除了外部竞争。

凭据、令牌不得填在 JVM 参数或健康路径中。敏感值放在管理员维护的 `env_files`；预览和审计只包含路径。环境文件内容不属于配置指纹覆盖范围，外部变更责任需明确；本期健康接口不支持需要认证密钥的端点。

## 4. 目录、实例配置与归属

### 4.1 目录契约

以下是拟采用的目标布局，不是当前已有目录：

```text
{app_home}/
  .smartops-instance.json         实例归属、资源占用、配置提交状态与指纹
  .deploy_version                实际 CURRENT 的版本兼容镜像，不表示健康通过
  .incoming/{operation_id}/      仅该令牌使用的上传暂存区
  releases/{version}/
    app.war                     校验后提交的不可变制品
    .sha256                     app.war 的 SHA-256
  CURRENT -> releases/{version}
  instance/                     固定 CATALINA_BASE
    conf/
      server.xml
      web.xml
      catalina.properties
      logging.properties
      Catalina/localhost/{context_name}.xml
    lib/                        保持空；首版不管理实例级共享依赖
    webapps/                    平台专用 appBase，只容纳本应用的展开副本
    work/                       平台可清理的该实例工作缓存
    temp/                       平台可清理的该实例临时数据
    logs/                       保留，不随发布/回滚清理
  .config-staging/{operation_id}/ 配置事务暂存
  .config-backup/{revision}/      上次配置事务快照，不随 WAR 自动回滚

/etc/systemd/system/{unit}.service
/var/lib/smartops/tomcat/
  registry.lock                 固定 inode 的主机资源注册表保护锁
  registry.json                 实例 ID、规范路径、unit、port、归属摘要
  locks/{instance_id}/
    gate.lock                   固定 inode；单次远端动作保护锁
    owner.json                  整个逻辑操作的持久占用记录
    last-result.json            最近完成结果，供断线后核验，不包含凭据
```

归属文件包含 `schema_version`、随机 `instance_id`、项目/服务/环境标识、规范化路径、unit、port、配置 revision/digest、文件清单和提交状态。项目标识用于审计，不单独构成远端身份：平台之间的数据库整数 ID 可能重号。后续操作必须匹配远端实例 ID、配置摘要和资源身份。

部署身份拥有版本、配置、状态、注册表与锁的写权限；运行账号只读制品/配置，只写 `webapps/work/temp/logs`。新建目录按上述边界设权限，不更改已有运行时、环境文件、账号或 sudo 配置。`app_home` 及控制目录不能由应用账号改写，控制路径中存在未知符号链接时拒绝操作。

应用上传文件、报表、持久缓存等必须外置。`webapps/work/temp` 被视为可再生目录，接入预览必须明确告知，不能把它们当业务数据目录。

### 4.2 Tomcat 配置生成

- 生成最小 `server.xml`：关闭远程 shutdown（`Server port=-1`），只创建一个业务 HTTP NIO Connector；不生成 AJP、Manager、Host Manager、示例应用或额外管理连接器。
- `Host` 固定 `autoDeploy=false`、`deployOnStartup=true`：不做运行期间自动部署扫描，启动时仍部署配置描述符。不能把关闭 autoDeploy 误解为关闭启动部署。
- 应用使用外部 Context XML，`docBase={app_home}/CURRENT/app.war`，位于 appBase 外，避免重复发现。context 由 XML 文件名决定，不额外写相冲突的 `path`。
- `reloadable=false`、`copyXML=false`，禁用 WAR 内嵌 Context 配置的自动接纳；外部 Context 描述符仍须能正常启动，纳入三个 Tomcat 系列的实际测试。
- `unpackWARs=true`。停机后清除该实例专用 appBase 的旧展开副本、work 和 temp，再启动，避免符号链接切到新 WAR 但仍运行旧缓存；应用日志、历史 releases、外置业务目录不清理。
- `web.xml`、`catalina.properties`、`logging.properties` 基于已预装 Tomcat 相应版本的模板生成受管副本，纳入指纹。不要把一种 Tomcat 版本的模板硬套到所有系列；模板不完整或读取失败阻止接入。
- systemd 使用 `Type=simple`、明确的非 root `User`、`KillMode=control-group`、停止/启动超时以及已有环境文件引用。默认 `Restart=no`，避免人工确认失败前自动重启造成状态反复；平台负责本次动作的启动与恢复，不提供后台无限重试。
- `ExecStart` 直接运行 `{java_home}/bin/java`，带平台控制的 catalina home/base、临时目录、JULI 日志配置、bootstrap/tomcat-juli classpath，主类为 `org.apache.catalina.startup.Bootstrap start`。不调用会展开 shell 参数的 `catalina.sh`，不承诺脚本专用 `JAVA_OPTS/CATALINA_OPTS` 生效。
- 默认采集 journal 中的控制台输出。Tomcat/应用另写文件日志时不自动接管，也不把“未采文件日志”判作部署失败。

### 4.3 接入与配置更新

GET 预览返回规范化配置、待生成的 unit/实例文件、目录清单、删除缓存边界、模板摘要及 `preview_digest`。生成依赖远端模板时需要只读探测，各主机模板不同则逐主机展示摘要。不得读取环境文件内容。

POST 接入要求管理员权限、服务归属校验、明确环境/主机集合、对应预览摘要及确认。配置或模板在预览后变化则拒绝陈旧确认，重新预览；不能以“曾经点过确认”永久授权覆盖。

接入过程在主机注册表与实例操作保护下完成：校验已存在非 root 运行账号及目录权限 → 检查运行时与资源冲突 → 暂存/验证配置 → 登记准备状态 → 写入文件/归属 → daemon-reload → enable。接入不启动应用，不安装系统组件。

首次接入仅接受不存在或真正空的目标根，且不存在冲突单元/注册记录；有相似 ExecStart 但无归属标记也拒绝覆盖。崩溃留下的部分接入目录必须走核验恢复，不能当空目录继续。

配置更新保持同一 `app_home`、unit 和 instance ID；修改根或 unit 属于迁移，本期不提供隐式迁移。其他关键配置（端口、context、账号、JDK/Tomcat 路径、JVM 参数、env_files 路径、readiness 等）必须管理员重新预览确认，且写入新配置前实例已停止、无 systemd 待执行 job、cgroup 无残余进程。

健康运行实例的合法停机入口放在配置更新向导：管理员明确选择“受控停止并更新”，确认停机影响、当前受管 revision 和目标 preview_digest。后台在同一 owner 内核对旧有效配置/归属 → 必要时摘流 → 严格停止并确认退出 → 提交配置事务，全程不释放逻辑占用。不能要求用户绕过锁手工 systemctl stop，也不能用尚未接入的候选配置指纹去否定合法的旧实例停机；旧文件必须匹配其已登记 revision，真实漂移仍拒绝。未明确选择此动作时，普通配置更新只接受原本已停止的实例。

停止失败不写配置；停止后更新失败按本节恢复旧配置，但不自动恢复运行或流量。成功也保持停止/摘流，明确展示“配置已更新，实例未启动”；后续启动使用用户单独发起的受锁保护重启任务。这样既保留“配置写入前必须停止”的门槛，又不增加无确认自动停机或更新后自动启动。

受控停机前将维护标志和摘流前的非敏感注册/权重快照持久保存到实例归属状态，配置事务备份/恢复不得丢弃它。后续重启必须明确确认结束维护，按新配置健康后才恢复这份流量快照并清除维护标志，不能把维护期间的零权重误当原值；原本就停用的流量也不强制开启。维护标志存在时只允许带结束维护确认的重启进入启动；其他发布、回滚和重启（包括定时任务）均拒绝，避免配置更新返回后被另一个任务意外启动。维护启动失败保留该标志与快照；这与因执行状态未知而保留的 owner 是两个不同状态。若本次停止失败但能确认旧应用及原流量均已恢复、没有配置变更，可撤销本次新建的维护标志；不能撤销此前已经存在的维护状态。

配置指纹由规范化运行配置、渲染模板版本、受管配置文件和 unit 的内容摘要组成；构建输入（如 artifact_pattern）不属于实例配置。发布/重启/回滚比较期望摘要、归属清单、受管文件及 systemd 实际加载的路径/启动参数；有效配置漂移一律阻止变更。环境文件只指纹其引用路径。

更新不是跨目录的单步原子操作：先备份旧配置并写 `configuring` 状态，逐项替换文件、处理旧 context 描述符、reload/enable 成功后才提交新 revision。普通异常恢复本次事务旧配置并 reload，实例保持停止；事务恢复失败或 SSH 失联标 `configuration_unknown`，保留锁和现场。处于未提交状态的实例不得启动/发布。管理员只能在核验停止且旧动作被隔离后，选择恢复备份或重新确认配置，不能靠重发请求跳过状态。

这属于“接入配置事务的失败恢复”，不是“WAR 版本回滚恢复配置”。备份保留用于管理员核验，本期不提供自动清理历史配置。

## 5. WAR 产物与运行时预检

### 5.1 本地制品

Maven 复用既有 build_order 和构建命令；构建完成后独立搜索 WAR。搜索范围为项目根和配置的构建模块目录，合并规范化后的候选再去重；不能在第一个目录命中就提前返回。

零候选报未找到；多个候选列出路径并要求收窄 artifact_pattern，不取最大/最新。构建得到 `dist/{service}-{version}.war` 及 `.war.sha256`。`build_type=none` 使用同一最终名称契约，缺旁文件或 SHA 不匹配直接失败，不偷偷重建或改写旁文件。

检查 WAR 是可读取的 ZIP、成员名不含绝对路径/穿越、无符号链接或重复目标条目；读取中央目录估计展开空间，不向平台任意目录解压。检查不能证明应用 Servlet API 和字节码兼容，兼容责任仍由运行验收承担。服务制品名兼容已有统一派生规则，不能由上传路径决定远端目录。

### 5.2 目标预检

远端需要 Linux/systemd、POSIX shell、`flock`、标准文件/哈希/路径工具，以及已安装的 Java/Tomcat。依赖命令在接入和操作前检查，缺失明确失败，不安装。首版锁目录要求本机支持可靠 flock 的本地文件系统，不支持把锁控制目录放到 NFS 等未验证共享文件系统。

校验 Java/Tomcat 实际版本、bootstrap/JULI jar、配置模板、账号读取/执行权限、控制目录归属、剩余空间、unit 与配置指纹、锁以及探活通道。应用账号权限探测所需工具亦列入接入预检，不能执行到停机阶段才发现依赖缺失。

磁盘需求同时考虑上传 WAR、展开后的总大小、保留旧版本和临时开销；不能只按压缩包体积判断充足。预检不清历史制品腾空间，也不先停止旧实例。

兼容目标：

| Tomcat 系列 | Java 最低版本 | 本平台状态 |
| --- | --- | --- |
| 9.0.x | Java 8 | 待真实 Linux/systemd 验证 |
| 10.1.x | Java 11 | 待真实 Linux/systemd 验证 |
| 11.0.x | Java 17 | 待真实 Linux/systemd 验证 |

这里只是最低组合，不保证任意更高 Java/Tomcat 补丁组合均可用。必须记录实际验证的发行版、Java/Tomcat 完整版本和 WAR 类型。Tomcat 9 与 10/11 的应用 API 代际不同，平台不进行包名转换。

### 5.3 不可变传输

每次上传使用唯一 `.incoming/{operation_id}`。仅在文件完整传输、远端 SHA 与本地旁文件一致后，才把包含 `app.war/.sha256` 的临时目录提交为 `releases/{version}`；暂存和 releases 在同一文件系统，以目录重命名提交。

目标版本存在时重算其 WAR SHA：相同内容复用，不改文件；内容不同、缺损或旁文件异常均拒绝覆盖，要求新版本号或管理员离线处理。检查存在和提交都在同一远端动作保护锁中，不能覆盖竞态中出现的目录。

SFTP 只写本操作随机暂存路径，绝不直接写 releases/CURRENT/配置。中断的上传不影响旧版；失联后不自动清理仍可能打开的暂存文件。被隔离的旧令牌即使继续完成 SFTP，也只能留下孤立暂存，不能提交或切换。并行预传以每主机独立操作占用执行，成功提交后释放；滚动发布重新加锁并复验，不能把预传成功等同发布预检成功。

## 6. 远端操作锁与异常恢复

### 6.1 双层保护协议

仅平台进程内存锁或本地 SQLite 锁不足以保护多个平台实例。使用目标主机持久占用记录加短时内核 flock：

1. 主机固定 `registry.lock` 保护实例注册和资源冲突校验；未接入时也先用该入口定位规范路径，避免两个平台给同一目录分配不同 instance ID。
2. 每实例固定 `gate.lock`。获取逻辑操作时先持有 gate，检查 owner 不存在，再原子写入随机 256-bit 令牌、operation ID、操作种类、发起平台/任务标识、开始时间和阶段。时间用于诊断，不作为抢占条件。
3. 每次会改变受管状态的远端动作，都持有 gate，并在锁内核对 owner 令牌后执行。动作脚本同步等待子命令，不通过后台 `&`、脱离会话或先释放 gate 再修改状态规避保护。
4. 命令间可以释放 gate，但 owner 必须跨预检、流量隔离、切换、健康验证、恢复和结果落盘持续存在。第二个逻辑操作发现 owner 就拒绝，不排队等 TTL。
5. 正常结束在 gate 内核对令牌并提交 last-result，最后移除 owner；gate 文件永不 unlink/重建，避免不同 inode 上同时加锁。

涉及注册表和实例 gate 时，固定顺序为 registry → gate；常规发布只取 gate，不在持 gate 时反向获取 registry。主机资源注册不串行化各独立实例的整个发布。

systemctl 返回不表示 unit 的所有 job 必然终结：释放操作前还需确认相关 job、cgroup 和预期终态。运行中的正常业务 JVM不持有 gate；仅远端动作及其同步子命令持有它。

### 6.2 锁覆盖的操作

发布、显式回滚、自动恢复、首台灰度回滚、重启、接入、配置更新（含明确确认的维护停机）和管理恢复均进入此协议。监控与日志只读，不抢占写操作；看到未提交动作时标“变更中/状态未确认”。上传仅能绕过 gate 写其独占暂存区，提交绝不能绕过。

锁是平台之间的协调协议，不是防御拥有目标机 root 权限的人。旧版平台或人工 systemctl 不认识新协议，绕过协议操作此类实例必须作为运维禁令写入使用说明，不能声称已被技术上隔离。正常配置维护走第 4.3 节受控流程，不依赖人工旁路停机。

### 6.3 失联、取消与管理员恢复

SSH 超时、平台崩溃或取消信号不证明远端已停止。若无法确认远端终态，不在 finally 中自动删除 owner，不按 TTL 抢锁，不把“平台进程不存在”当远端任务结束证据。

取消在停机前且确认没有变更，可安全结束并释放；发布在停机/切换后取消必须优先执行有界的稳定化（恢复旧版本或停止首次失败实例），任务仍记为取消/失败。配置维护取消则以保持停止并完成或恢复配置事务为稳定态，不自动启动旧应用；尚未真正停止的维护动作按停止失败规则判断现场。无法稳定化则保留 owner，标 `operation_unknown`；不能继续下一主机。

首版管理员恢复是单独的“检查 → 确认 → 隔离旧令牌 → 解除占用”接口，沿用管理员权限与服务归属校验。只读检查返回远端 owner 摘要、当前指向、unit/job/cgroup 和配置事务状态；确认提交携带检查摘要，现场变化则拒绝。

恢复时获取 gate（失败即说明动作可能仍在执行，不强制删锁），在 gate 内再次核验后隔离旧令牌。所有迟到命令重新核验令牌后必须失败，因此不会在新操作后继续切换。尚存 systemd job、未知子动作或部分配置事务必须先人工确认/处理；不能仅因为 gate 空闲就认为可解锁。恢复接口不自动杀进程、不清业务目录、不替用户选择应用版本；可解除的实例必须已核验为健康且状态一致，或完全停止且无未完成配置事务。若此前有未确认的 Nacos 请求，还必须确认发起方已停止/被隔离且在途请求已终结；当前流量查询正常不能证明迟到请求不会再修改它，无法确认时仍保留占用。

孤立 SFTP 只能继续写旧暂存目录；确认其结束前不回收该目录、不复用 operation ID。解锁前后、操作者、理由、令牌的非敏感摘要和核验结论写审计。原始令牌、凭据和环境内容不返回前端。

## 7. 发布、回滚、重启与结果语义

### 7.1 每主机快照

加锁并通过归属/配置检查后读取实际 CURRENT、对应制品 SHA、运行/应用健康及版本标记，形成该主机本次操作快照。不同主机可以有不同旧版本，不把首台版本复制给其他主机作为恢复基线。

CURRENT 的有效目标是实际版本依据，`.deploy_version` 是其兼容镜像，SQLite 是展示缓存。链接越界、制品缺失或两个远端版本证据不一致时报告漂移，停止变更，由管理员核验；不盲目信任数据库覆盖现场。

普通发布的自动恢复默认使用本机快照；显式 `--previous-version` 作为操作者指定的失败恢复覆盖时，也必须逐主机验证该版本存在、SHA 完整并记录实际快照和覆盖目标。没有任何历史部署的首次发布仍没有自动恢复基线。自动版本号推荐可以聚合主机版本，但推荐值不进入失败恢复快照。

### 7.2 正常发布

1. 完成本地校验；目标加锁后做运行时、配置、空间、目标/恢复制品及探活通道预检。恢复基线无效时在停机前拒绝常规更新，不能偷偷降低为“失败不恢复”。
2. 上传并不可变提交 WAR。Nacos 配置存在时，在开始停止前将本应用实例摘流；摘流失败阻止停机。
3. 在发出 stop 之前记录 `target_modified` 与阶段。执行 `systemctl stop`，确认单元停止、无待执行 job、主 cgroup 无进程；不能只检查 MainPID=0，更不能 `stop || true`。
4. stop 失败则不换 CURRENT、不清缓存。查询能证明旧版仍健康时报告“停止失败，旧版本仍服务”；否则报告状态未确认并保留占用，不能假定旧版仍在运行或直接恢复流量。
5. 原子替换 CURRENT，并以临时文件重命名更新 `.deploy_version`。二者不是单个文件系统事务：owner 中记录切换阶段；任一步失败进入恢复/未知路径，不能把半完成状态当成功。
6. 仅清理该受管实例专用 `webapps/work/temp` 中的可再生内容，不跟随符号链接进入外部目录；保留目录、权限、日志及历史制品。
7. 启动实例，检查 systemd 状态和应用 HTTP 健康。成功后恢复 Nacos 原有注册/权重策略，再记录每主机结果与数据库缓存。平台不合成不存在的 Nacos 注册。
8. 落盘可核验终态后释放 owner。DB 写入失败保留远端事实并报告“远端完成、平台状态同步失败”，不为修缓存而回滚健康应用，不输出无条件全成功。

发布按现有滚动/灰度节奏串行推进；任一主机发布失败、恢复失败或状态未知都停止后续主机，不因恢复成功而把本次发布标成功。

### 7.3 HTTP 健康通道

拟采用同一 SSH 连接的 `direct-tcpip` 隧道，从平台发 HTTP 到目标机 `127.0.0.1:{port}`，无需目标机 curl/Python，也不要求平台直连业务端口。接入预检确认 SSH 允许这一精确目的地址的转发；没有应用运行时，“连接拒绝”和“转发被禁止”必须区分。转发能力未知/被禁则阻止部署，不自动修改 sshd 配置或退化为进程健康。

HTTP GET 使用第 3 节组合后的路径，不继承平台代理环境，不跟随重定向。仅 200 且可选固定正文条件满足才成功；所有 3xx、非 200、超时、断开和正文不匹配均失败。单请求最多 5 秒且不超过总截止时间，响应正文读取上限 1 MiB，超限失败；日志只输出状态和匹配结果，不保存响应正文。

首版不支持 TLS Connector、额外虚拟主机/Host 头、认证健康端点或任意 URL。HTTP 成功用于判断服务可用，不代表应用业务回归通过。重启、回滚、接入后的首次部署和持续监控复用同一判定；监控做单次有界探测，不等待整个发布级轮询超时。

### 7.4 失败恢复与显式回滚

自动恢复：取得日志片段（失败仅警告）→ 核对恢复制品和当前阶段 → 严格停止 → 切回旧 WAR → 清可再生缓存 → 启动 → 同样 HTTP 检查 → 仅恢复成功才重新接入流量。每主机最多一次自动恢复；恢复再次失败停止滚动并保留现场，不循环换版本。

旧制品缺失/损坏时，显式回滚在停机前拒绝；自动恢复若遇到该情况，报告“恢复受阻”，保留/尽可能停止失败实例并如实记录停止结果，不报告“已回滚”。运行时或固定配置改变导致旧 WAR 无法工作也属于恢复失败，不自动降级 Tomcat/JDK。

首次部署失败且无可恢复版本时，停止失败实例并确认退出，保留新制品、CURRENT 和日志用于排查，报告“首次发布失败，无可回滚版本”。若停止或通信也失败，报告“首次发布失败，实例状态未确认”，保留 owner，不谎称已停止。

显式回滚与首台灰度回滚复用同一操作入口。首版 WAR 显式批量回滚按主机顺序执行，一台恢复失败/未知即停止后续；不复用旧模式的全量并行“尽量多回滚”语义。显式回滚本身失败不再自动反向回滚到另一个版本，避免恢复环路。首台灰度回滚使用该主机本次发布记录的恢复基线。

### 7.5 重启与统一结果

WAR 重启不传制品、不改 CURRENT，但必须加锁、校验配置/制品、摘流、严格停止再启动并执行 HTTP 验证；健康超时就是任务失败。失败时尽可能停止不健康实例、保留摘流状态；重启不悄悄切成别的版本。

主机操作返回结构化结果，至少包含 `operation_status`、`phase`、`current_version`、`recovery_target`、`process_state`、`app_health`、`recovery_status`、`traffic_status`、`lock_state`、错误摘要。恢复状态枚举为 `not_needed/succeeded/blocked/failed/unavailable/unknown`；unknown 不能转为 succeeded。

| 情况 | 结果与展示 | 后续 |
| --- | --- | --- |
| 新版健康且必要流量恢复完成 | 发布成功 | 正常释放，允许继续 |
| 新版失败，旧版恢复并健康 | 发布失败，恢复成功 | 正常记录终态，停止继续滚动 |
| 旧包缺失/校验失败 | 回滚/恢复受阻 | 不声称旧版运行，停止继续 |
| 已切回旧版但 HTTP 失败 | 恢复失败 | 保留错误现场，阻止继续 |
| 首次失败，实例已停止 | 发布失败，无可回滚版本 | 保留产物日志；确认终态后可释放 |
| SSH 失联/停止结果不明/配置半提交 | 状态未确认 | 保留 owner，管理员核验 |
| 应用健康但 Nacos 上线失败 | 应用就绪，流量恢复失败 | 不回滚健康应用，停止继续，明确流量状态 |

Nacos 的离线状态在恢复受阻/失败/未知时不得被 finally 无条件改成上线。外部 Nacos 调用也必须有有界超时；若平台无法确认调用终态，保留操作占用并要求核对流量状态，远端令牌本身不能隔离已经在外部服务执行的请求。

远端稳定、恢复失败且实例已确认停止时，可以记录失败终态后释放 owner，以便显式修复；“保留现场”不等于永久锁死。只有状态/配置/外部动作未确认时才必须保留占用。最终汇总和通知使用真实结果，不套用旧的“发布中断，已回滚失败服务器”固定文案。

| 组件 | 负责 | 明确不负责 |
| --- | --- | --- |
| `deploy_strategies/tomcat_config.py` | 配置规范化、校验、Context 命名、指纹输入 | SSH 写入、任务编排 |
| `deploy_strategies/war_tomcat.py` | 注册模式、产物/能力契约、版本推荐、调用 WAR 操作服务 | 继承旧 stop/rollback 成功语义 |
| `deploy_strategies/tomcat_instance.py` | 模板渲染、归属、接入与配置事务 | 任意人工实例接管 |
| `deploy_strategies/remote_operation.py` | 远端注册表、owner/gate、令牌隔离、结果持久化 | 自动 TTL 抢锁、代替权限系统 |
| `deploy_strategies/tomcat_lifecycle.py` | 主机快照、发布/回滚/重启、稳定化、结构化结果 | 对旧七种模式改行为 |
| `deploy_strategies/tomcat_health.py` | SSH HTTP 单次探活及有界轮询 | 任意 URL 代理、目标机依赖安装 |

`base.py` 增加显式 opt-in 的严格主机操作接口，旧策略默认沿用现有代码。`Deployer.deploy_server`、首台灰度回滚、`rollback_all` 在该能力启用时调用新入口并消费结果，不再进入旧异常汇总与无条件上线分支；外层 build/通知/任务取消/灰度等待复用，但不得泄漏首台 previous_version 到其他主机。

WAR 仍属于 `is_process=True`，以便复用 unit 指标、journal 和主机视图。`process_config.py`、`service_unit.py` 必须显式分发到 WAR 配置/渲染，避免落入 Python 默认分支。重启任务在通用进程分支前识别严格操作能力，使用相同 SSH 凭据合并与生命周期。

构建增加独立 WAR selector 与产物映射；YAML 导入导出往返保留规范配置。既有服务记录无需迁移默认值；确需存持久结果的最小字段扩展必须兼容历史任务，不把凭据放进 extra/结果 JSON。

unit 预览/接入扩展对 WAR 返回实例文件清单和摘要，旧模式仍保留原返回字段。新增检查/确认式操作恢复入口，只允许管理员，所有涉及服务的路径都验证 project/service/environment 归属；HTTP 207 的每主机成功/失败不能被前端合并成全部成功。部署与重启沿用现有角色权限，接入/配置更新/解锁不得降为普通部署权限。

首版不提供自动接入/强制覆盖 CLI 快捷参数；CLI 发布也要求实例已通过管理员流程接入。服务表单标出 WAR 端口、Context、健康路径及“固定配置不随 WAR 回滚”；主机抽屉展示配置漂移、锁占用与恢复状态，只有合适角色显示恢复入口。

## 9. 观测、版本与审计

继续复用服务卡片、每主机抽屉、任务日志及 journal 采集，不建设独立监控系统。WAR 增加 `process_status`、`app_health`、`config_status`、`operation_state` 和 `recovery_status`；整体 online 仅用于进程运行、应用健康且配置一致的主机。

运行但健康失败显示“不健康”，SSH/隧道不可达显示“探测失败/未知”，停止与未部署分开。操作持有 owner 时显示变更阶段，不能以旧缓存给出新的健康成功结论；指标失败允许保留带时间戳的旧值，不能伪装实时。

实际 CURRENT 版本与健康独立：新版本指向但启动失败仍显示新版本及失败状态；回滚成功更新为旧版本。读取 `.deploy_version` 的兼容路径不够证明 WAR 的链接一致性，需扩展 WAR 专用证据采集。监控只按变化写穿缓存，不改既有 CPU 前样本/主机去重机制；读取版本、owner、结果时若发现阶段变化，按过渡态处理，不用半个快照覆盖已确认回滚历史。

`service_host_state.current_version` 表示现场观察版本，不能直接用于自动恢复决策；previous_version 保留操作历史基线，监控轮询不自行制造回滚链。DB 不可写时仍保留远端事实，下轮可重试状态同步。

审计记录接入/更新/恢复、操作者、项目服务环境、主机、配置摘要、变更类型与每主机结果。审计和预览不含私钥、密码、env 值、原始锁令牌或 HTTP 正文。应用自行输出的 journal 仍沿用平台日志权限和脱敏规则，不保证第三方应用日志天然没有敏感内容；取日志失败不能阻止恢复。

### 10.1 分片门禁（不是实施任务计划）

| 分片 | 保护或解锁的业务路径 | 验证信号与回退边界 |

| B 归属、锁、接入 | 两个平台不能接管或同时改一个实例 | 双进程竞争、陈旧确认、半提交恢复、令牌隔离测试；未启动可恢复接入事务 |
| C 严格生命周期 | 发布、失败恢复、显式回滚、重启都不误报成功 | 状态矩阵和故障注入；取消/断线 fail closed；不继续滚动 |
| D 观测、表单、包装 | 操作者能区分版本/健康/恢复结果，便携包也能走完整入口 | JS/API/导入闭包测试及便携启动冒烟，不能只测首页 |
| E 实际兼容与回归 | 已有服务不退化，声明支持的 Tomcat/Java 组合可运行 | Linux/systemd 三组记录及全量质量门禁；缺环境明确阻断支持声明 |

A → B → C 是核心依赖；D 可围绕稳定契约拆开验证，E 必须在对外宣布完成前收口。Windows/Kubernetes 不夹带到这些切片中。

| 主题 | 必须覆盖的输入/故障 | 验收断言 |
| --- | --- | --- |

| 归属 | 未标记目录/单元、路径别名/嵌套、跨平台同实例、端口冲突 | 拒绝接管；同主机注册唯一 |
| 配置事务 | 预览过期、未确认停机的运行中更新、写文件/reload/enable 失败、断线 | 未确认不停止；写配置前停止；旧配置可恢复；半提交不可发布 |
| 维护闭环 | 健康运行→确认停机→更新、维护中取消、迟到启动/定时任务、明确结束维护 | 全程同一 owner；更新后保持停止；未确认不启动；健康后恢复原流量；失败保留维护快照 |
| 停止 | stop 非零、MainPID=0 但 cgroup 有进程、尚有 job | 不换链接、不删缓存，不忽略错误 |
| 缓存 | 旧解压 WAR、work/temp、异常符号链接、外置业务文件 | 只清受管可再生内容；日志、历史制品、外部数据不动 |
| 健康 | 200/3xx/非200、正文匹配失败、超时、超大响应、隧道拒绝 | 不跟随重定向、不退化为进程成功、无目标 curl 依赖 |
| 失败恢复 | 新版失败旧版健康、缺旧包、旧包坏、旧版健康再失败 | 分别恢复成功/受阻/失败；发布总结果仍失败 |
| 首次发布 | 无旧版、启动失败、停止失败 | 停止失败实例或报未知，不编造回滚成功 |
| 多主机 | 旧版本不同、显式覆盖缺包、首台灰度回滚、中途失败 | 本机快照不串用；失败停止继续 |
| 锁 | 双任务/双进程/两个平台、迟到指令、SFTP继续、管理员抢锁 | 所有入口互斥；旧令牌不可提交；不按 TTL 抢占 |
| 取消/失联 | stop 前取消、切换后取消、命令未返回平台断线 | 稳定化后结束或保留 owner，不能裸释放 |
| 流量 | 摘流失败、恢复失败、上线调用结果未知 | 不在坏实例上无条件上线；状态未知阻止继续 |
| 结果 | DB 写失败、rollback 抛异常、显式回滚健康失败、重启健康超时 | 日志/通知/API 同一结论，失败不能算成功 |
| 权限 | 非管理员接入/解锁、跨项目服务 ID、陈旧恢复确认 | 拒绝并无目标写入；审计不含敏感值 |
| 回归 | 七种旧模式、YAML 往返、监控前样本和版本写穿、便携包模块 | 原契约不变；新增 WAR 所需入口真实可导入 |

### 10.3 真机验证

分别以 Tomcat 9 + Java 8、Tomcat 10.1 + Java 11、Tomcat 11 + Java 17 的 Linux + systemd 环境验证：首次接入不启动、根和非根 context、多版本实际响应切换、旧展开缓存清理、健康失败恢复、首次失败停止、非 root 进程、重启、配置漂移、双平台竞争及 SSH 中断后人工恢复。

每组记录系统发行版、systemd/SSH/Tomcat/Java 精确版本、测试 WAR API 代际、实际命令结果和日志。官方最低版本说明或 mock 通过不算真机证据。当前没有可用真机执行记录，三组均为“未验证”。

### 10.4 全量与交付验收

执行仓库 Python 全量测试、`scripts/quality_gate.py` 对应门禁、前端测试，以及 Windows 便携包模块完整性、初始化/登录和 WAR 配置/预览依赖导入冒烟。打包时核查根模块 `service_unit.py` 及新增依赖实际在包内，不能以安装了平台即认为接入功能可用。

当前文档阶段没有执行新功能测试，也没有重新运行 v0.4.0 的历史测试；历史通过结果不作为 WAR 验证。实现交付应明确区分自动化通过、实际环境通过、未验证和明确不支持。版本发布、Git 提交/推送、真实目标操作仍需用户另行授权。
