# 配置管理重设计规格：傻瓜式运维创作

> 日期：2026-08-17
> 状态：已由用户确认（视觉伴侣 approve）
> 范围：配置管理全量重构——信息架构、项目内组织、服务/环境/流水线/服务器的新增与编辑方式、环境↔服务器绑定入口
> 硬约束：**后端 API 零改动**，全部能力消费现有接口（config_routes 已具备：环境 6 大块 JSON、服务器绑定 bind/unbind/reorder、连接测试 /servers/test、YAML 导入导出）

## 1. 背景与目标

现有配置管理将服务/环境/流水线/服务器的新增与编辑平铺为裸表单 + 手写 JSON 文本框，新手面对专业术语（`build_order`、`nacos_groups`、`snailjob_group`、`registry.mode`）无从下手，学习成本高、配置靠猜。

**目标：让不熟悉平台的人也能完成"可视化运维创作"——傻瓜式操作，降低学习成本。**

| 对象 | 现状痛点 | 本次手段 |
|---|---|---|
| 环境 | 6 大块配置（registry/nacos/mysql_snailjob/ssh/build/deploy）全部是裸 JSON 文本框 | 模板一键填充 → 分组语义表单 → 高级模式开关 → 绑定服务器步骤 |
| 流水线 | stages 手写 JSON 数组（service_id 是什么、怎么排全靠猜） | 拖拽画布式阶段编排 + 模板 + 实时发布命令预览 |
| 服务 | 15+ 字段平铺一屏，无分组无说明 | 复制现有服务 + 分组表单 + 每字段白话解释 |
| 服务器 | 角色自由文本、密码"继承环境级"语义不明、无连接验证 | 角色卡片选择 + 继承凭据开关 + 就地校验 + 保存时自动测试 SSH |
| 环境↔服务器绑定 | 后端 API 齐全但前端**无入口**（现有盲区） | 环境表单内"绑定服务器"步骤：勾选 + 排序 |
| 信息架构 | 扁平标签页，无引导、无概览 | 配置工作台首页（统计卡片 + 快速开始 + 最近项目 + 空态引导顺序） |

## 2. 关键决策（与用户确认）

| 决策点 | 结论 |
|---|---|
| 信息架构 | 方案 C：配置工作台（全局统计卡片 + 最近使用项目 + 快捷操作引导） |
| 项目内组织 | 项目仪表盘（概览卡片 + 问题徽章）+ 服务/环境/流水线/服务器子页 |
| 流水线编辑 | 拖拽画布式（服务池 + 纵向阶段流 + 串/并行开关） |
| 环境 JSON 策略 | 表单为主 + 高级模式开关（同一份数据双向转换，不丢内容） |
| 预设模板 | 环境、流水线都提供 |
| 服务创建 | 复制现有服务 + 分组表单 |
| 改动范围 | 全量重构配置管理（含补环境↔服务器绑定入口） |

## 3. 技术方案

| 项 | 决策 |
|---|---|
| 技术栈 | 原生 HTML/CSS/JS（沿用），零构建链、零 npm 依赖；拖拽用原生 HTML5 Drag & Drop，不引第三方库 |
| 路由 | hash 路由：`#/config`（工作台）、`#/config/p/<pid>`（项目仪表盘）、`#/config/p/<pid>/services|environments|pipelines|servers`（子页） |
| 数据流 | 表单统一维护一份 JS 数据对象；高级模式切换 = 同一对象的 YAML/JSON 序列化与反序列化，切换不丢内容 |
| 模板 | 前端静态定义（JS 常量），不落库；环境 5 模板、流水线 4 模板 |
| 复制 | 前端从列表接口取全量字段搬运（list 接口已返回全部字段），复制时剔除 id/project_id 等标识 |
| 绑定与测试 | 消费现有 API：`GET/POST /environments/<eid>/servers`、`DELETE`、`PUT /environments/<eid>/servers/order`、`POST /servers/test` |

## 4. 信息架构：配置工作台

```
#/config（配置工作台首页）
├── 顶部统计卡片：项目 / 服务 / 环境 / 流水线 / 服务器(SSH 健康 x/y) / 用户
├── 快速开始：新建服务 / 新建环境 / 编排流水线 / 添加服务器（每张卡写明"做什么、大概多久"）
├── 最近使用的项目（点击进入项目仪表盘；localStorage 记录访问时间）
└── 空态引导：一个项目都没有时显示推荐顺序「新建项目 → 添加服务器 → 新建服务 → 新建环境 → 编排流水线」

#/config/p/<pid>（项目仪表盘）
├── 项目上下文条：项目名 + 描述 + SSH 健康徽章 + 问题徽章（如"1 个环境未绑定服务器"）+ 编辑按钮
├── 四大概览卡片：服务 / 环境 / 流水线 / 服务器（数量 + 说明 + "管理"按钮）
└── 概览页签内容：最近发布记录（消费 /api/tasks）

#/config/p/<pid>/services|environments|pipelines|servers（子页）
└── 子页签：概览 / 服务 / 环境 / 流水线 / 服务器 / YAML 配置（导入导出入口沿用）
```

数据来源拼装：`/config/projects`（含三类计数）、`/config/servers`（含 conn 状态）、`/api/users`（用户数）、`/api/tasks?limit=10`（最近发布，项目仪表盘按 project 过滤）。

## 5. 环境表单（模板 → 分组表单 → 高级模式 → 绑定服务器）

### 5.1 流程

新建：**① 选择模板 → ② 填写配置 → ③ 绑定服务器 → ④ 校验并保存**（弹窗内步骤条引导）；编辑：直接进入 ②。

### 5.2 模板选择（5 张卡片）

| 模板 | 自动填充 | 用户只需 |
|---|---|---|
| 标准 Java 微服务环境 | registry(mode=direct, namespace 占位)、nacos(url 占位, group=DEFAULT_GROUP)、mysql_snailjob(占位)、ssh(user=root, port=22)、build(maven_profile 留空自动推导)、deploy(health_timeout=120, health_interval=5, canary_wait=60) | 服务器地址等差异项 |
| K8s 容器环境 | registry(mode=push, host 占位)、deploy 分区 | 仓库地址、命名空间 |
| 轻量单机环境 | 仅 ssh + deploy 两分区 | 约 1 分钟完成 |
| 从现有环境复制 | 加载选中环境的全部 6 大块 JSON | 改名字和差异项 |
| 空白环境 | 不预填任何值 | 逐项填写 |

每张卡写明"自动填充什么、只需改什么"；卡片底部注明"模板可在保存后随时更改，不会丢失已填内容"。

### 5.3 分组表单（核心）

6 大块 JSON 拆为可折叠分区（外加基本信息区），头部含分区名 + 白话描述 + "已填写"状态徽标；用不到的分区折叠跳过：

1. **基本信息**：环境名称（必填，白名单 `[A-Za-z0-9_-]`，保存后不可改）、Maven profile 下拉（prod/test/dev/custom，留空按环境名自动推导）
2. **镜像分发**（registry）：分发模式下拉（direct=直传服务器无需仓库 / push=推送到镜像仓库，选项带白话解释）、镜像命名空间（必填）、仓库地址（仅 push）、仓库账号/密码（可留空用环境变量）
3. **服务注册中心 Nacos**（nacos）：地址（必填）、命名空间 ID（留空=public）、默认分组、账号/密码（可留空用环境变量）
4. **SnailJob 任务调度数据库**（mysql_snailjob）：host/port/database/username/password（可折叠跳过）
5. **服务器连接 SSH**（ssh）：用户/端口/密码（提示"敏感密码建议环境变量 SSH_PASSWORD"）
6. **本地构建工具链**（build）：maven_home/java_home（留空自动探测）、maven_profile
7. **发布行为**（deploy + 独立列）：project_root（本地源码根目录）、docker_compose_path（服务器 docker-compose.yml 路径，DB 独立列）、health_timeout、health_interval、canary_wait、dist_dir、remote_tmp_dir

字段通用形态：必填星标 + `?` 提示 + 占位示例 + 底部解释文字（如"direct = 本机构建后 scp 到服务器 docker load，不需要镜像仓库"）。

### 5.4 高级模式开关

- 弹窗头部开关「高级模式：直接编辑 YAML」；打开后表单区替换为等高的 YAML 编辑器（textarea + 语法高亮 CSS）
- **表单与 YAML 共享同一份数据**，切换时自动双向转换，提示条明示"不会丢失任何已填内容"
- YAML 结构 = 现有 deploy.yaml 的 registry/nacos/mysql_snailjob/ssh/build/deploy 段，保存时与表单模式走同一提交逻辑

### 5.5 绑定服务器步骤（填补现有盲区）

- 展示项目全部服务器：复选框（已绑定默认勾选）+ IP + 角色徽标（first/follower）+ SSH 连通状态（绿/红，来自 /servers 的 conn 字段）+ ↑↓ 排序 + ✕ 移除
- 未绑定的服务器带"＋ 添加"快捷入口
- 底部图例："first = 首个发布并灰度观察；follower = 其余按顺序发布。角色在服务器列表中维护，这里仅选择与排序"
- 保存提交：新建 = POST 环境 + 逐条 POST 绑定；编辑 = PUT 环境 + diff 后的 bind/unbind + PUT order

## 6. 流水线画布编辑器（拖拽式）

### 6.1 布局

```
┌─────────────────────────────────────────────────────────────┐
│ 头部：流水线名称输入 · 构建优先开关(build_first) · 模板下拉    │
│       实时发布命令预览（python deploy_pipeline.py --pipeline …）│
├───────────┬─────────────────────────────────────────────────┤
│ 服务池     │ 阶段区（纵向阶段流）                               │
│ 🔍 搜索    │ ┌ 阶段卡 ──────────────────────────────────────┐ │
│ ⚙️ svc-a 用│ │ 阶段名输入 · 串行/并行开关 · 🗑删除            │ │
│ 🛒 svc-b 用│ │ 服务块（可拖拽排序/移出）· 版本徽标(可选)        │ │
│ 🛒 svc-c   │ └──────────────────────────────────────────────┘ │
│（已用置灰） │  ＋ 添加阶段                                      │
└───────────┴─────────────────────────────────────────────────┘
```

### 6.2 交互规则

- **服务池**：项目全部服务；已被任一阶段使用的置灰 + "用"标记；顶部搜索过滤；拖动到阶段容器加入（HTML5 Drag & Drop，容器高亮放置区）
- **阶段卡**：阶段名可编辑输入框；串行/并行开关（切并行时橙色提示"并行阶段内的服务会同时发布，请确保目标服务器不冲突"）；服务块容器支持拖入/拖出/拖内排序；服务块 ✕ 移出；阶段 🗑 删除（非空时二次确认）
- **服务级版本**：服务块上可选版本徽标（点击弹出 version / previous_version 输入，对应 stages[].services[].version / previous_version 覆盖命令行参数；mixed-version 场景）
- **阶段顺序**：阶段左侧圆点拖拽调整整卡顺序
- **模板**：全量发布（网关→基础设施→业务→任务，多阶段）/ 仅业务服务 / 仅定时任务 / 空白流水线
- **说明**："阶段按从上到下顺序执行，某阶段失败则停止后续阶段"
- **实时预览**：底部生成发布命令 `python deploy_pipeline.py --pipeline <name> --version <ver>`，帮新手理解配置最终形态
- 数据模型：stages[].name / stages[].parallel(bool) / stages[].services[].service_id / version / previous_version；保存时后端 _check_pipeline_stages 校验引用存在性（前端拖拽天然满足，服务删除保护沿用后端）

## 7. 服务表单（复制 + 分组 + 字段说明）

### 7.1 复制快捷方式

弹窗顶部常驻「📋 从现有服务复制」下拉：选中后把该服务全部字段带入下方表单（含 build_order/nacos_groups/dubbo_services/log_error_keywords 列表），提示"选中后自动带入下方全部字段，改名字和差异项即可"；服务名唯一性校验在保存时执行。

### 7.2 分组（4 组，字段对齐现有 DB 列）

1. **基本信息**：服务名（必填，--project 参数）、镜像短名 image_name（必填，完整镜像 = {namespace}/{image_name}:{version}）、Git 仓库路径 git_repo（必填，发布成功打 v{version} tag；多服务共用仓库填仓库目录名）、docker-compose 服务名 service_name（默认同服务名）
2. **构建配置**：构建顺序 build_order 行编辑器（行 = 模块名 + 相对路径 + goal 下拉(install/package) + 可选 extra_profile + ⇅ ✕，底部"＋ 添加构建步骤"；说明"common-build/api 一般 install，最终服务模块 package"）、Docker 上下文目录 docker_context、Dockerfile 路径 dockerfile
3. **注册中心与任务调度**：Nacos 分组 nacos_groups 标签输入器（回车添加、✕ 删除；说明"服务在多个分组注册时须全部列出；不填则使用环境默认分组"）、Dubbo 额外服务 dubbo_services（同标签输入器，可选）、SnailJob 分组 snailjob_group（说明"普通微服务留空即可"）
4. **健康检查与日志**：健康检查端口 health_port、健康检查 URL health_url（说明"{ip} 会被替换为当前服务器 IP；留空则退化为容器状态+日志检查"）、启动失败关键字 log_error_keywords 标签输入器（默认预填 ERROR/Exception/Failed to start）、启动前清空日志目录 clear_log_dir（说明"留空则不清空"）

## 8. 服务器表单（继承凭据 + 角色卡片 + 校验 + 测试）

### 8.1 表单结构

1. **连接信息**：服务器 IP（必填）、Nacos 注册内网 IP nacos_ip（说明"NAT 环境下与 IP 不同才填，相同留空"）、**角色卡片选择**——first·首台（"最先发布，灰度观察无异常后再发布其余服务器"）/ follower·后续（"按绑定顺序跟随发布，用于集群扩容"），两卡片带白话解释，必选其一；提示"同一环境至少 1 台 first"
2. **SSH 连接凭据**：默认开关「使用环境级凭据」开启——仅展示说明条"本台服务器使用环境级 SSH 凭据（root@22 · 密钥 ~/.ssh/id_rsa_deploy），大部分服务器共用一套登录方式，无需逐台填写"；关闭开关才显示覆盖字段（登录用户/SSH 端口/连接方式：密钥或密码）。留空字段 = 不提交（后端 NULL = 导出时继承环境级，与现有三态语义一致）
3. **备注**（可选）：textarea，说明"仅用于识别服务器用途，不影响发布逻辑"

### 8.2 保存前自动校验（不打断填写）

- 必填缺失 / IP 格式（IPv4 段 0~255）/ 重复 IP（与 /servers 列表比对）→ **字段下方就地标红提示**，光标留在原处，不弹窗
- 全部通过后「保存并测试连接」按钮才高亮

### 8.3 保存时自动测试 SSH（消费 POST /servers/test）

- 测试面板分项展示：网络可达（ping 延迟）/ 端口开放 / 密钥认证 / 密码认证（自动回退提示）/ Docker 可用，各带 ✓/✕/⚠ 与耗时细节
- 失败项给出**可执行建议**（如"把 ~/.ssh/id_rsa_deploy.pub 添加到该服务器的 authorized_keys，保存后再次测试"）
- 提供「重新测试」与「仍要保存」兜底（沿用现有语义：连接失败仅提示，不阻断保存）

### 8.4 保存成功反馈

成功 toast + 步骤条（① 添加服务器 → ② 新建服务 → ③ 新建环境并绑定 → ④ 编排流水线）+ 下一步引导按钮「去绑定环境 →」（跳转环境页对应编辑弹窗的绑定步骤）。

## 9. 校验与错误处理统一约定

- **字段级校验**：必填/格式/重复就地标红（环境名白名单、服务名项目内唯一、IP 格式与重复、流水线名唯一），不弹窗打断
- **保存失败**：toast 顶部红色提示（展示后端 error message，如"服务被流水线 stages 引用"）
- **删除**：一律二次确认；服务被流水线引用时展示后端错误提示
- **加载态**：面板级 shimmer 骨架屏；接口失败面板内局部错误态 + 重试按钮
- **空态**：统一空态组件（图标 + 文案 + 引导按钮），如"一个项目都没有？点击右上角新建项目…"

## 10. 组件与文件组织

├── config-home.js               # 配置工作台首页（统计/快速开始/最近项目/空态）

├── config-env-form.js           # 环境表单（模板/分组/高级模式/绑定）
├── config-pipeline-editor.js    # 流水线画布（拖拽）
├── config-service-form.js       # 服务表单（复制/分组）
├── config-server-form.js        # 服务器表单（凭据继承/校验/测试）
└── config-form-helpers.js       # 共享：字段说明渲染、标签输入器、就地校验、YAML 转换

## 11. 测试计划

1. **环境闭环**：模板新建（各模板跑一遍）→ 分组表单微调 → 高级模式切换往返（内容不丢）→ 绑定服务器（勾选/排序/解绑）→ 保存 → 编辑回显一致 → 导出 YAML 结构与手动配置等价
2. **流水线闭环**：模板填充 → 拖入/拖出/排序/移出服务 → 阶段增删/排序/串并行切换 → 服务级版本设置 → 保存 → 重新打开还原 → 发布命令预览正确
3. **服务闭环**：复制现有服务 → 改名保存 → 编辑 → 被流水线引用时删除被拒 → 删除
4. **服务器闭环**：IP 格式错/重复/必填缺失就地标红 → 保存并测试连接（成功与失败两路径）→ 仍要保存兜底 → 绑定环境后环境表单可见
5. **工作台**：统计卡片数据正确、快速开始跳转、最近项目进入仪表盘、空态引导顺序
